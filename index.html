01 / ★ Featured · AI + real-time

ZipRun: AI-Powered Order Reassignment Engine

Code ↗

An agentic re-planning loop for delivery fleets. When a rider goes offline or an order is about to miss its SLA, it finds the affected orders, recommends a new rider with an LLM, and streams the suggestion live to a human operator for approval.

Problem

Dispatchers reshuffled orders by hand whenever riders dropped off. It was slow and error-prone, and SLAs were missed silently.

Solution

Heartbeat-based offline detection triggers background re-planning. The LLM considers zone and capacity, and its suggestions arrive over SSE for one-click approval.

Outcome

Re-planning runs on its own and dispatch never stops. Acceptance rate, fallback frequency and confidence are tracked for AI and rules separately.

Request flow
  1. Rider heartbeatstatus events
  2. Kafkaorder events
  3. Re-plan engineSLA · zone · capacity
  4. LLM routerGemini → Groq → rules
  5. PostgreSQL · Redis@Version locking
  6. SSE → Angularhuman approval ✓
Java 17Spring Boot 3.3PostgreSQLKafkaRedisResilience4jGeminiGroqAngularDockerNginxGitHub ActionsFlyway
Engineering decisions & trade-offs 5 decisions⌄
  1. Three-tier fallback: Gemini → Groq → deterministic rules, each behind a Resilience4j circuit breaker, so an AI provider outage never stops dispatch.rule-based picks are less context-aware, but they're always available
  2. Human-in-the-loop by design. The AI recommends and an operator accepts, rejects or reassigns. Every action is logged so AI and rule acceptance rates can be compared.one extra click per order in exchange for trust and an audit trail
  3. Optimistic locking (@Version) stops two concurrent re-plans from double-assigning the same order, without holding row locks.retries on conflict, which is cheap because contention is rare
  4. SSE instead of WebSockets for live suggestions. Server-to-client is the only direction needed, it's simpler to operate, and it passes cleanly through Nginx.no client→server channel, so REST handles operator actions
  5. Reproducible from day one. Flyway migrations, one-command docker compose up, and GitHub Actions CI.more setup up front, but no environment drift
02 / ★ Featured · data pipeline + AI

LeadLens: B2B Lead Qualification Pipeline

Code ↗

Turns raw B2B lead exports into a ranked, ready-to-call list. It cleans and de-duplicates, verifies emails and phones, enriches companies by reading their public websites, scores leads 0–100 against a custom buy box, and drafts AI outreach briefs.

Problem

Lead exports are messy: duplicates, dead emails, shared inboxes and no context. Reps spent hours qualifying leads before making a single call.

Solution

A clean → verify → enrich → score → act pipeline with A/B/C/X tiers, transparent scoring reasons, natural-language filters and HubSpot/Salesforce export.

Outcome

5,000 rows parsed, de-duplicated and saved in 4.5 s, and 13.4 s end to end with verification and scoring. The first rows appear in under 1 s.

Processing pipeline
  1. CSV importCommons CSV · dedup
  2. VerifyMX · libphonenumber
  3. Enrichjsoup crawler · 6 workers
  4. Score0–100 · tiers A/B/C/X
  5. Claude briefstructured output
  6. Call list · CRMHubSpot · Salesforce
Java 17Spring Boot 3.3PostgreSQL (Neon)FlywayCaffeineClaude APIjsoupAngular (signals)Multithreading
Engineering decisions & trade-offs 5 decisions⌄
  1. Fixed worker pool (6 threads), with network I/O kept outside DB transactions, so slow websites never hold database connections or block imports.bounded throughput, but predictable resource usage
  2. Tiered Caffeine caching: MX results 24h, robots.txt 6h, enrichment 24h per domain. This removes repeated network calls for leads that share a company.data can be up to a day old, which is fine for qualification
  3. LLM with structured outputs plus a template fallback. Briefs are always generated, even when the AI call fails or returns malformed output.fallback briefs are generic but never block the user
  4. An ethical, secure crawler. It respects robots.txt and Retry-After, never bypasses bot challenges, verifies email by DNS only (no SMTP probing), and guards against SSRF.some sites can't be enriched, which is the right call
  5. Single deployable. The Angular SPA (~93 kB gzipped) is bundled into the Spring Boot jar and served from the same origin. That means no CORS and one artifact to ship.frontend and backend release together

Approach

How I work

The principles behind my engineering decisions, each backed by something I've actually shipped.

Design for failure

Every dependency will fail eventually. I add circuit breakers, timeouts, retries with backoff, and fallbacks that degrade gracefully instead of breaking.

In practiceZipRun's Gemini → Groq → rules failover keeps dispatch running through AI outages.

Measure, then optimize

I profile first and fix the real bottleneck: query plans, indexes, caching, payload size. Then I verify the gain with numbers.

In practice25% lower DB execution time and 30% lower API latency at Quinnox.

Secure by default

Authentication, authorization and secrets belong in the first design review. Least-privilege RBAC/ACL, audit trails, and no secrets in code.

In practiceJWT + RBAC + ACL with audit logging, Vault-managed secrets, and an SSRF-guarded crawler.

Async where it counts

I decouple with events when consumers have different scaling needs or failure domains, and I keep things synchronous when simple is enough.

In practiceKafka-driven workflows for real-time processing, with SSE for one-way live updates.

Automate the boring parts

CI/CD, migrations, tests and repeatable deploys. If I do something twice by hand, the third time it's scripted.

In practiceJenkins/Azure DevOps pipelines with blue-green deploys, and 40% fewer manual processes.

Own it, then multiply it

I take ownership from client requirements through to production, then raise the team's level with reviews, RCAs, standards and mentoring.

In practiceSole technical point of contact for enterprise clients, and mentor to junior engineers.
